# ระบบการติดตามงานวางและจัดทำผังเมือง (UPMS)

UPMS ใช้ค้นหาผังเมือง ติดตามความคืบหน้ารายจังหวัดและเขตตรวจราชการ นำเข้า Excel/CSV ส่งออก Excel/CSV และจัดเก็บเอกสารประกอบ หน้าเว็บพัฒนาด้วย React และ TypeScript ส่วน API ใช้ Express บน Node.js และ SQLite ข้อมูลที่แก้ไข หมายเหตุ ไฟล์แนบ และประวัติการเปลี่ยนแปลงคงอยู่หลังเริ่ม API ใหม่

[กลับหน้าเลือกเวอร์ชัน](../README.md) · [เปิดคู่มือ PHP](../php/README.md)

## เริ่มใช้งานบนเครื่อง

เตรียม Node.js 22.13 ขึ้นไปและ npm (ทดสอบด้วย Node.js 24) เพื่อใช้ `node:sqlite` โดยไม่ต้องติดตั้งบริการฐานข้อมูล เปิดเทอร์มินัลที่โฟลเดอร์หลักของ repo แล้วเข้าโฟลเดอร์แอปเพื่อติดตั้งแพ็กเกจครั้งแรก

```sh
cd project-typescript-react-express-nodejs-api
npm run install:all
```

จากโฟลเดอร์แอป ให้รันคำสั่งนี้เพื่อเปิดหน้าเว็บและ API พร้อมกัน

```sh
npm run dev
```

เปิด [หน้าเว็บ UPMS](http://localhost:5173/) หรือ [ตรวจสถานะ API](http://localhost:4000/api/health) หากพอร์ต 5173 มีโปรแกรมอื่นใช้อยู่ ให้เปิด URL ที่ Vite แสดงข้างคำว่า `Local` ในเทอร์มินัล กด `Ctrl+C` ในเทอร์มินัลเมื่อต้องการหยุดระบบ

## โครงสร้างโปรเจกต์

## เมนูและการใช้งาน

- ติดตามผังเมือง: รายงานสถานภาพผังเมือง ผังตามขอบเขตการปกครอง ผังตามเขตตรวจราชการ สรุปสถานภาพปัจจุบัน ค้นหาผังเมือง และแผนดำเนินงาน
- จัดการข้อมูล: ผังเมืองรวมเมือง/ชุมชน ผังในขั้นตอน ม.35 งานประเมินผล ขั้นตอนดำเนินการ ขั้นตอนการประเมิน จังหวัดและส่วนผังเมืองรวม รายการหมายเหตุ หมวดหมู่หมายเหตุ และเหตุผลผังพิจารณาดำเนินการ
- รายงาน: ข้อมูลผังเมือง ความก้าวหน้า ผังดำเนินการ ผังยกร่างกฎหมาย และส่งออก CSV ภาษาไทยสำหรับเปิดใน Excel พร้อมพิมพ์รายงาน
- คณะติดตามฯ 1–7: แสดงรายการตามเขตตรวจราชการที่กำหนดในข้อมูลเริ่มต้น
- ระบบ: ทะเบียนผู้ดูแลข้อมูล บันทึกกิจกรรม และข้อมูลติดต่อประสานงาน

หน้า [ติดต่อประสานงาน](http://localhost:5173/#contacts) แสดงเบอร์จำลอง `00 000 0001` ถึง `00 000 0004` สำหรับ สผม. ส่วน 1–4 และ `00 000 0005` ถึง `00 000 0006` สำหรับ ศทส. 1–2 ตามลำดับ

รวม 48 เมนู แต่ละหน้ามี hash URL เช่น `#dashboard`, `#plans`, `#import`, `#module-workflowCases`, `#catalog`, `#map`, `#accounts` และ `#logs` จึงเปิดลิงก์ตรงและใช้ปุ่มย้อนกลับของเบราว์เซอร์ได้ หน้าแรกยังเป็นผังตามขอบเขตการปกครอง

เมนู “รายงานข้อมูลผังเมือง” (`#reports`) เปิดแผนผังต้นไม้ตาม `DPT_UPMS2/report/tree-chart.php` มีหัวข้อ “ผังกำหนดการใช้ประโยชน์ที่ดิน” กล่องประเภทผัง เส้นเชื่อม และส่วนติดตามผังด้านล่าง โครง HTML/CSS สร้างจากต้นฉบับด้วย `scripts/sync-tree-report.mjs` โดยตัด PHP/JavaScript เดิมออก แยกขอบเขต CSS และเชื่อมตัวเลขกับ Express API กดจำนวนเพื่อเปิดรายการย่อย เช่น `#reports/list/new`, `#reports/list/eva5` และ `#reports/list/bbfY-1` พร้อมค้นหา ดูรายละเอียด/หมายเหตุ และย้อนกลับได้

ยอดผังเมืองรวมจังหวัด 70 และผังเมืองรวม EEC 1 เป็นค่าอ้างอิงเดียวกับที่ PHP ต้นฉบับกำหนดไว้นอก `tb_cityplan` อยู่ใน `server/src/data/treeReport.ts` ส่วนทุกสาขาเมือง/ชุมชนคำนวณจากข้อมูลผังที่จัดเก็บใน SQLite ยอดรวมบนสุดรวมสองค่าอ้างอิงนี้ด้วย เงื่อนไขประกาศใช้บังคับในโมเดลนี้ใช้ `effectiveStatus` ที่มีผลหรือสิ้นสุดบังคับใช้แทนฟิลด์ `cp_status` ของ PHP

UI checks เทียบกล่อง สี และตำแหน่งของรายงานนี้กับ `tree-chart.php` เดิมที่ render ด้วย SQLite ในหน่วยความจำ โดยใช้ข้อมูลชุดเดียวกันที่ 1440px และ 390px ตรวจจำนวนที่กดกับรายการย่อย และกรณีมีผู้ดำเนินการ EEC ทั้งกรมฯ/อปท. ภาพและผลวัดอยู่ใน `.tmp/tree-report-*`

หน้า “ผังตามขอบเขตการปกครอง” ยึด `../DPT_UPMS2/app/show_extra.php` และ `show_page_park-keth.php`: แผนที่ด้านซ้าย คำอธิบาย 8 สถานะ กล่องภาคพร้อมจำนวนผัง แถบสถานะ และจังหวัด 5 ช่องต่อแถว กดชื่อภาคเพื่อดูแผนที่ภาค/กล่องจังหวัด กดจังหวัดหรือจำนวนเพื่อดูรายงานในระบบ พร้อมย้อนกลับ ค้นหา และเปิดรายละเอียด/หมายเหตุได้ เช่น `#regions/region/1` และ `#regions/region/1/province/24`

หน้า “ผังตามเขตตรวจราชการ” (`#keths`) ใช้โครงเดียวกันตาม `DPT_UPMS2/app/show_extra_keth.php` พร้อมแผนที่หลัก แผนที่ย่อย 1–18 คำอธิบาย 8 สถานะ และจำนวนรายจังหวัด กดชื่อเขตเพื่อดูจังหวัดในเขต เช่น `#keths/keth/1` รายชื่อเขตใช้ `ref_province` จาก `dpt_cityplan.sql` ซึ่งเขต 1 มีชัยนาท พระนครศรีอยุธยา ลพบุรี สระบุรี สิงห์บุรี และอ่างทอง กรุงเทพมหานครมีรหัสเขต 0 จึงไม่รวมใน 18 เขตตามต้นฉบับ

หน้า “รายงานสถานภาพผังเมืองรวม” (`#dashboard`) ยึด `app/report.php` / `app/t2.php` แสดงกราฟสถานภาพ ลักษณะงาน ขั้นตอนวางผัง ขั้นตอนปรับปรุง และส่วนรับผิดชอบ ใช้ Chart.js 4.4.0 ที่คัดลอกจาก PHP ในโปรเจกต์ รองรับสลับกราฟ/ตารางและกดแท่งกราฟหรือจำนวนเพื่อดูรายการย่อย เช่น `#dashboard/list/status/active`

หน้า “สถานภาพผังเมืองปัจจุบัน” (`#status`) ยึด `app/status_currentx.php` / `status_currentx_pro.php` แสดงตาราง 3 คอลัมน์สีตามภาพต้นฉบับ: สิ้นสุดใช้บังคับ มีผลบังคับใช้ และเปิดพื้นที่ใหม่ แบ่งยกร่างกฎหมาย ย้อนดำเนินการ ตาม พ.ร.บ. เร่งรัดปรับปรุง และไม่ระบุ กดจำนวนเพื่อดูรายชื่อด้านล่างและเปิดข้อมูลเพิ่มเติมได้ สถานภาพนี้ใช้ฟิลด์ `trackingState` ในข้อมูลเริ่มต้น แก้ไขได้จากหน้ารายละเอียดผัง การจำแนกเป็นข้อมูลที่เก็บไว้ ไม่ได้อนุมานข้อกฎหมายจากลำดับขั้นตอน

สีสถานะใช้ข้อมูลความก้าวหน้าที่เก็บไว้ในระบบ ช่องไม่ระบุขั้นตอนพิจารณาจากขั้นตอนหลัก/ย่อยที่เป็นศูนย์ สัญลักษณ์เตือนใช้ฟิลด์ `nextStepPending` และแถบเสนอหน่วยงานใช้ขั้นตอน 8 ย่อย 2/4/5/6/8 ตามต้นฉบับ ข้อมูลขั้นตอนย่อย 2 ที่ยังไม่มีในโมเดลแสดงเป็น “—”

## ข้อมูลเริ่มต้นและขอบเขต

มีผังเมืองเริ่มต้นครอบคลุม 77 จังหวัด / 5 ภาค / 18 เขตตรวจราชการ พร้อมหมายเหตุ หน่วยงาน ขั้นตอน หมวดหมู่ เหตุผล และทะเบียนผู้ดูแลข้อมูล ข้อความบนหน้าจอใช้ชื่อรายการและรหัส `UPMS-xxx`

ฐานข้อมูลเริ่มต้นอยู่ที่ `server/data/upms.sqlite` และสร้างพร้อมข้อมูลตั้งต้นเฉพาะเมื่อยังไม่มีฐานข้อมูล กำหนด `UPMS_DB_PATH` เพื่อเลือกตำแหน่งอื่น หรือ `:memory:` สำหรับการทดสอบ ไฟล์ฐานข้อมูลและ WAL ไม่ถูกติดตามด้วย Git การรีสตาร์ตไม่ล้างข้อมูล ปุ่ม “คืนค่าข้อมูลเริ่มต้น” จะล้างการแก้ไข ประวัติ และไฟล์แนบทั้งหมด จึงมีข้อความยืนยันก่อนดำเนินการ

โมเดลโหลดข้อมูลเข้าแคชในโปรเซสและบันทึกผ่าน SQLite transaction ก่อนตอบว่าสำเร็จ ใช้ตารางผัง หมายเหตุ บันทึกกิจกรรม ขั้นตอน รายการจัดการ ประวัติ ไฟล์แนบ และโมดูลธุรกิจ แยก primary/foreign key และเก็บฟิลด์โดเมนเป็น JSON มี revision ตรวจการเขียนจากข้อมูลเก่าเพื่อป้องกันอีกโปรเซสเขียนทับ เมื่อเกิด conflict API ตอบ 409 และโหลดข้อมูลล่าสุดกลับเข้าแคช ควรรัน API หนึ่งโปรเซสต่อฐานข้อมูล ทะเบียนผู้ประสานงานแยกจากบัญชีที่ใช้เข้าสู่ระบบและตรวจสิทธิ์จริง

การแบ่งงานคณะติดตามฯ ใช้รายการมอบหมายที่จัดเก็บในฐานข้อมูลและแก้ไขได้ที่ `#module-committees` ค่าตั้งต้นอิงการแบ่งเขตใน `php/mock_db_setup.php` โดยยังไม่ได้อ้างว่าเป็นคำสั่งแต่งตั้งจริง แผนดำเนินงานคำนวณวันที่แบบรวมวันแรกตามขั้นตอนและเงื่อนไขคำร้อง แล้วบันทึกแผนที่สร้างไว้เป็นชุดแยกจากการแก้เกณฑ์เวลาภายหลัง

ทะเบียนผัง งาน ม.35/ประเมิน ขั้นตอนย่อย หมายเหตุ รายงาน แผนที่ การนำเข้า/ส่งออก ไฟล์แนบ การบำรุงรักษา และสิทธิ์ผู้ใช้ทำงานด้วย TypeScript โดยไม่เรียก PHP ขณะใช้งาน ฐานข้อมูลใช้โมเดลใหม่ จึงไม่ได้เป็น MySQL-schema compatibility layer หรือย้ายข้อมูลหน่วยงานจริงที่อยู่นอก repo ประวัติเริ่มบันทึกตั้งแต่ใช้เวอร์ชันนี้ ค่าระยะเวลาตั้งต้นมาจากฉบับสาธิตและปรับได้ผ่านหน้าจอ ไม่ได้เพิ่มกฎที่ไม่มีอยู่ในต้นฉบับ

### เช็กลิสต์การย้ายจาก PHP

คำสั่ง `npm run migration:audit` ตรวจไฟล์ PHP ที่ Git ติดตามในโฟลเดอร์ `php/` แล้วสร้าง [รายการเทียบไฟล์กับ TypeScript](./docs/migration-inventory.json) ปัจจุบันมี 210 ไฟล์: 202 ไฟล์เชื่อมกับกลุ่มฟังก์ชันที่พัฒนาใหม่ และ 8 ไฟล์เป็นข้อมูล โหลด asset ตัวอย่าง UI หัวข้อเปล่า หรือส่วนที่ถูกปิดไว้เดิม เช่น `chatbot.php` ที่คืน HTTP 204 ไฟล์หลายรุ่นและไฟล์สำรองใช้ฟังก์ชันเดียวกันใน TypeScript จึงไม่คัดลอกหน้าซ้ำเพื่อเพิ่มขนาดโค้ด

เช็กลิสต์ระบุหน้าที่และไฟล์ปลายทาง ไม่ใช่การนับจำนวนฟังก์ชันหรือรับรองว่า payload PHP เดิมทุกแบบยังเรียกได้ API ใหม่เป็น REST การทดสอบแยกตรวจพฤติกรรมจริงของแต่ละกลุ่มงาน และต้นฉบับ PHP คงอยู่สำหรับเทียบรายละเอียด

### บัญชีและสิทธิ์

ก่อนมีบัญชีจริง ระบบคงโหมดสาธิตแบบ PHP เดิม เลือก Superadmin/Admin/Guest ได้จากเมนูชื่อผู้ใช้ สร้างบัญชี Superadmin แรกผ่าน `#accounts` เพื่อเปิดการเข้าสู่ระบบและปิดการเลือกสิทธิ์อย่างอิสระ หรือกำหนด `UPMS_ADMIN_USERNAME` และ `UPMS_ADMIN_PASSWORD` ก่อนเริ่ม API ครั้งแรก (รหัสผ่าน 12–200 ตัวอักษร) ระบบไม่ใช้รหัสผ่านที่ฝังในซอร์ส และไม่เขียนรหัสผ่านลง log

รหัสผ่านจัดเก็บด้วย scrypt และ salt สุ่ม ใช้ opaque session cookie แบบ HttpOnly/SameSite Strict อายุ 8 ชั่วโมง และตรวจ CSRF สำหรับการเขียนข้อมูล Guest อ่านได้แต่แก้ไขไม่ได้ Admin แก้ข้อมูลงานได้ ส่วนบัญชี ขั้นตอนอ้างอิง จังหวัด คณะติดตาม และคืนค่าฐานข้อมูลต้องใช้ Superadmin API เป็นผู้ตรวจสิทธิ์ การเปลี่ยนรหัสผ่านหรือปิดบัญชียกเลิกเซสชันเดิม และปิดผู้ดูแลสูงสุดคนสุดท้ายไม่ได้ การคืนค่าข้อมูลธุรกิจไม่ลบบัญชีและเซสชัน

### นำเข้าและส่งออกข้อมูล

เปิด `#import` หรือเมนู **นำเข้าข้อมูล Excel / CSV** ดาวน์โหลดแม่แบบ กรอกข้อมูล ตรวจไฟล์ และกดยืนยันนำเข้า ระบบอ่านแผ่นงานแรก รับไม่เกิน 1,000 แถว/5 MB ต่อครั้ง ไม่รันสูตรในเซลล์ และไม่รองรับไฟล์ `.xls` เก่าหรือไฟล์เข้ารหัส ชื่อผังในจังหวัดเดียวกันต้องไม่ซ้ำ หากมีแถวผิดจะไม่บันทึกส่วนใดเลย ตัวอย่างรอยืนยันอยู่ในหน่วยความจำ 10 นาทีและใช้ได้ครั้งเดียว หากรีสตาร์ตระหว่างรอยืนยันให้ตรวจไฟล์ใหม่

คอลัมน์บังคับคือ `name` และ `provinceId` หรือชื่อจังหวัดในคอลัมน์ `province` แม่แบบมีแผ่นงานรหัสจังหวัดซึ่งเป็นรหัสในระบบนี้ คอลัมน์เสริม: `stage`, `category`, `owner`, `operator`, `budgetYear`, `currentStep`, `health`, `isEec` รองรับหัวคอลัมน์ภาษาไทย เช่น `ชื่อผังเมือง`, `จังหวัด`, `ปีงบประมาณ` และชื่อเดิม `cp_name`, `cp_province`, `cp_eec` เฉพาะฟิลด์ที่ระบุไว้ ไม่ได้นำเข้า dump ฐานข้อมูลเดิมโดยตรง

`category`: `general`, `m35`, `evaluation`; `health`: `on_track`, `slight_delay`, `moderate_delay`, `severe_delay`, `unscheduled`; `currentStep`: 0–8; `isEec`: `true/false`, `1/0`, `ใช่/ไม่ใช่`; `budgetYear`: ตัวเลข 4 หลัก ค่าอื่นใช้ตัวเลือกเดียวกับหน้าเพิ่มผัง เมื่อไม่ระบุฟิลด์เสริมใช้ค่าเริ่มต้นเดียวกับการเพิ่มผังผ่าน API

ไฟล์ส่งออก `.xlsx` เป็นรายงานข้อมูลทั้งหมดและมีคอลัมน์อ่านอย่างเดียว จึงใช้ไฟล์แม่แบบสำหรับนำเข้าใหม่ ส่วนปุ่ม CSV เดิมส่งออกตามตัวกรองที่เลือก

### เอกสารและประวัติ

เปิดรายละเอียดผังเพื่อแนบภาพหรือ PDF ได้สูงสุด 20 ไฟล์ ไฟล์ละ 5 MB ดาวน์โหลดแบบ attachment พร้อม `nosniff` ชื่อไฟล์ภาษาไทยคงเดิมและไม่ถูกใช้เป็น path บนเครื่อง เมื่อแก้สถานะ ชื่อ หมวดหมู่ หรือขั้นตอน ระบบบันทึกเฉพาะฟิลด์ที่เปลี่ยนจริงพร้อมค่าก่อน–หลัง ประวัติและไฟล์แนบลบตามผังเมื่อผู้ใช้ยืนยันลบผัง

## รันเวอร์ชัน build

รันสองคำสั่งนี้จากโฟลเดอร์แอปเพื่อให้ Express ให้บริการทั้งหน้าเว็บและ API ที่พอร์ตเดียวกัน

```sh
npm run build

```

เปิด http://localhost:4000 หากเปิดผ่าน Apache โดยตรง ต้องกำหนด reverse proxy `/api` ไปที่ Express

## ตรวจสอบ

คำสั่งติดตั้ง รัน และ build ใช้ไฟล์ในโฟลเดอร์ TypeScript ได้โดยตรง ส่วน `sync:php` และการทดสอบเทียบหน้าจอกับต้นฉบับต้องใช้ชุดไฟล์อ้างอิงเดิมของผู้พัฒนา (`DPT_UPMS2` และข้อมูลอ้างอิงที่ระบุด้านล่าง) โฟลเดอร์ `php/` ใน repo เป็นฉบับสาธิตสำหรับรันแยกกัน

```sh
npm run typecheck
npm run test:api
npm run test:operations
npm run test:ui
npm run migration:audit
```

API checks ใช้ฐานข้อมูลและพอร์ตแยก ครอบคลุมข้อมูลอ้างอิง ตัวกรอง CRUD ผังและข้อมูลจัดการ หมายเหตุ ขั้นตอน บันทึกกิจกรรม การคืนค่า และข้อมูลนำเข้าที่ไม่ถูกต้อง

Operations checks ใช้ SQLite ในหน่วยความจำและไฟล์ชั่วคราวแยกจากแอปจริง ตรวจการคงข้อมูลข้ามโปรเซส rollback/ID counters, stale write, Excel/CSV, ไฟล์แนบ, ประวัติ, ความสัมพันธ์บริษัท–โครงการ–อุปกรณ์, งบบำรุงรักษา, ขั้นตอนและวันครบกำหนด, คำร้อง, ชุดข้อมูลสถานภาพ, การจัดกลุ่มจังหวัด/คณะ, login/roles/CSRF/ยกเลิกเซสชัน และเช็กลิสต์ไฟล์ต้นฉบับ ส่วน UI checks ตรวจครบ 48 เมนู พร้อมขั้นตอนนำเข้าจริง แนบ/ลบไฟล์ บันทึก workflow สร้างโครงการ/อุปกรณ์/แผนบำรุง ดูงบรายปี บันทึกชุดข้อมูล เลือกจังหวัดบนแผนที่ และสร้างบัญชีแรกที่ 1440px รวมถึงหน้ามือถือ 390px

GitHub Actions ใน `.github/workflows/typescript.yml` ตั้งค่าให้ตรวจชนิดข้อมูล build และรัน `npm test` เมื่อ push สาขา main หรือเปิด pull request ที่แก้แอป TypeScript

UI checks build โปรเจกต์และเปิด Chrome/Edge แบบ headless ด้วย server และ browser profile แยก ตรวจทุกเมนู รายการที่เลือก ข้อความบนหน้าจอ การจัดการหมวดหมู่ การค้นหา หมายเหตุ การพิมพ์ และเมนูบนคอมพิวเตอร์/มือถือ กำหนด `CHROME_PATH` หากไม่ได้ติดตั้งเบราว์เซอร์ในตำแหน่งมาตรฐาน ภาพตรวจหน้าจอบันทึกใน `.tmp/` การตรวจใช้ Kanit ที่เก็บในโปรเจกต์

ถ้ามี PHP และโฟลเดอร์ `DPT_UPMS2` การตรวจจะ render `app/show_extra.php` และ `nav1.php` เดิมด้วยข้อมูลเริ่มต้นชุดเดียวกัน โดยแทนที่ส่วนเชื่อมต่อฐานข้อมูลด้วยตัวอ่านข้อมูลในหน่วยความจำ จึงไม่ติดต่อฐานข้อมูลเดิม จากนั้นโหลดธีมและ AdminLTE ของต้นฉบับในเบราว์เซอร์ เทียบตำแหน่ง ขนาด ฟอนต์ และสีขององค์ประกอบหลักที่ 1440px และ 390px โดยยอมให้ตำแหน่งต่างกันไม่เกิน 1px ภาพและผลวัดอยู่ที่ `.tmp/design-*` กำหนด `PHP_PATH` หาก PHP ไม่อยู่ที่ `C:/xampp/php/php.exe`
